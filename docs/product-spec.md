# Nevocean — продуктовая спецификация

> Документ описывает систему **как она реализована в коде**, а не как она
> задумывалась. Раздел [14. Статус функционала](#14-статус-функционала) явно
> разделяет реализованное, сделанное текущей задачей, следующий этап и то, что
> требует внешних доступов. Календарь Nevocean — собственный, внешних
> календарных интеграций в системе нет.
>
> В пользовательской документации используется название **Nevocean**.
> Внутренние идентификаторы (таблицы, пакеты, домен `nevodevs.kg`) сохраняют
> исторические имена — массовое переименование ради регистра бренда не
> проводится.

## 1. Позиционирование

**Nevocean — корпоративная система управления процессами компании.**

Это не «CRM с довесками»: CRM — один из модулей. Система закрывает полный
операционный контур:

- **задачи и личные доски** сотрудников;
- **сотрудники и отделы** с правами и составом;
- **CRM**: лиды, воронка, встречи, сделки;
- **продажи**: дневник сеттеров, встречи клоузеров, сводки;
- **финансы**: транзакции, счета, долги, зарплаты и комиссии;
- **аналитика**: дашборд, план/факт KPI, отчёты, экспорт;
- **внутренние процессы**: баг-репорты, NevoLabs, API-ключи для интеграций.

Ключевой принцип архитектуры: **один источник истины на сущность**. Сумма
сделки живёт только в `Deal.amount`, оплаты — только в графике оплат, встречи
CRM — только в `Meeting`. Производные значения (остаток, просрочка, статус
сделки) не хранятся, а вычисляются, чтобы не могли разойтись с фактами.

Валюта — сом, все суммы хранятся **целыми числами**.
Даты хранятся в **UTC**, отображаются в **Asia/Bishkek (UTC+6)**.

## 2. Роли и права

### Базовые роли (`User.role`)

| Роль | Описание |
|---|---|
| `admin` | Администратор: полный доступ к сотрудникам, настройкам, любым доскам и задачам |
| `staff` | Сотрудник: свои задачи, свои лиды, доступные отделы |

### Дополнительные признаки

| Признак | Влияние |
|---|---|
| `is_founder` | Доступ к скрытым разделам (`admin_only` отделы, доски `founder`), расширенные уведомления |
| `position` | Функциональная роль внутри отдела (см. ниже) |

### Функциональные роли отдела продаж (`User.position`)

| Позиция | Права |
|---|---|
| `Сеттер`, `Руководитель продаж` | Создание и редактирование встреч, ведение лидов |
| `Клоузер`, `Финансовый директор` | Проведение встреч и смена их статуса; финдиректор дополнительно управляет графиком оплат |
| `Промпт-инженер`, `Тимлид` | Проекты (боты), личные доски |
| `Бэкенд`, `Главный тех лид` | Общая доска «Очередь бэкенда» |
| `Менеджер качества` | Доска ОКК |

### Доски

| Тип | Просмотр | Редактирование |
|---|---|---|
| `personal` | Все | Владелец и админ |
| `backend_queue`, `qcc` | Все | Все (общая работа) |
| `founder` | Только `is_founder` | Только `is_founder` |
| `lab_project` | Админ, founder, участники NevoLabs | Те же |

### Права на график оплат

Изменять график и фиксировать оплаты могут: `admin`, `is_founder`,
`Финансовый директор`, а также **сеттер и клоузер конкретного лида**.
Удалить платёж с уже подтверждённой оплатой может только `admin`.

### Приватность личных данных

- Личные задачи **не раскрываются** другим сотрудникам.
- Календарь по умолчанию показывает только собственные события.
- Администратор может открыть календарь сотрудника — в рамках существующих
  административных прав на управление сотрудниками.
- Аватар: свой меняет любой пользователь, чужой — только `admin`.

## 4. CRM и жизненный цикл лида

### Модель лида

Контакты (имя, компания, телефон, WhatsApp, Instagram, email, адрес, сайт,
отрасль, размер), связи (источник, услуга, этап, сеттер, клоузер), работа
(следующее действие и его дата, комментарий), атрибуция (см. §12) и статус
(`active` / `archived`).

Финансовые поля `potential_amount` / `actual_amount` **устарели**: они
сохраняются только как зеркало для legacy-читателей, синхронизируются на
backend и **не показываются пользователю**. Каноническая сумма — `Deal.amount`.

### Жизненный цикл

```
Новый лид → Созвон → Встреча → Договор → Ожидание оплаты → Оплачено → Разработка
                                                   ↘ Минус
```

Этап **«Демо-тест» выведен из активной последовательности** (архивирован
миграцией `018`). Строка этапа, лиды и вся история переходов сохранены;
лиды перенесены на «Созвон» с системным комментарием в истории.

### Переходы и их побочные эффекты

| Этап | Что требуется | Что происходит |
|---|---|---|
| Встреча | дата, клоузер | Создаётся `Meeting` (с комментарием и продолжительностью) |
| Договор | сумма сделки | Обновляется `Deal.amount`, создаётся стартовый график оплат |
| Ожидание оплаты | сумма, ожидаемая дата | То же + `expected_payment_date` |
| Оплачено | сумма и дата оплаты | Оплата распределяется по графику; **этап меняется только при полной оплате** |
| Минус | причина отказа | Фиксируются причина и комментарий |

**Правило неполной оплаты:** если внесённая сумма меньше суммы сделки, оплата
сохраняется в графике, сделка получает статус `partial`, но лид **остаётся на
текущем этапе**, а пользователь получает сообщение с остатком. Частичная оплата
не может «закрыть» сделку.

### Защита от дублей

- По телефону — HTTP 409 с карточкой существующего лида и выбором
  «открыть» / «всё равно создать».
- По `external_lead_id` — HTTP 409 (основа идемпотентности для будущего webhook).

### История

- `LeadStageHistory` — все переходы (включая системные).
- `LeadActivity` — касания (звонки, сообщения, комментарии).
- `timeline` — объединённая лента: создание, переходы, подтверждённые оплаты.
- Архивные этапы **остаются читаемыми** в истории.

## 5. Воронка продаж

Воронка — **представление той же страницы `/leads`**, а не отдельный раздел.

- Адрес: `/leads?view=funnel`; список — `/leads?view=list` (по умолчанию).
- Старый `/funnel` делает redirect на `/leads?view=funnel`.
- В меню — один пункт «Лиды и воронка».
- **Фильтры общие для обоих представлений** (период, этап, источник, услуга,
  сеттер, клоузер, поиск) и сохраняются при переключении; состояние
  отражается в URL.
- Бизнес-логика не дублируется: обе вьюхи используют общие компоненты
  (`LeadFiltersBar`, `CreateLeadModal`) и общий набор фильтров API.

Воронка показывает этапы с количеством и суммой, выбранный этап — таблицей
лидов с колонками **Сумма сделки / Оплачено / Остаток**, днями на этапе и
действиями перехода. Архивные этапы колонками не отображаются.

Подсветка строк: просроченное следующее действие — красным, превышение
`norm_days` — жёлтым, выигранная сделка — зелёным.

## 6. Сделки и график оплат

### Источник истины

| Величина | Где живёт |
|---|---|
| **Сумма сделки** | `Deal.amount` — единственное каноническое значение |
| **Оплачено** | `Deal.paid_amount` — пересчитывается из подтверждённых платежей |
| **Остаток** | Не хранится: `max(amount − paid, 0)` |
| **Статус сделки** | Выводится: `pending` / `partial` / `paid` |

Термин **«Потенциал» удалён** из интерфейса, форм, таблиц, воронки, отчётов и
экспорта. Пользователь видит только «Сумма сделки», «Оплачено», «Остаток».

### График оплат (`deal_payments`)

Каждый транш содержит: плановую дату и сумму, фактически оплаченную сумму и
дату оплаты, статус, способ оплаты, счёт, комментарий, автора и дату изменения.

Статусы: `Запланирован`, `Частично оплачен`, `Оплачен`, `Отменён`, и
вычисляемый `Просрочен`.

### Инварианты (проверяются на сервере)

1. Сумма графика **не может превышать** сумму сделки.
2. Сумма сделки не может стать меньше уже запланированных платежей.
3. Оплата по траншу не может превышать его плановую сумму.
4. Суммарная оплата не может превышать сумму сделки.
5. **Просрочка вычисляется сервером** из плановой даты и невыплаченного
   остатка — она не хранится и не может устареть.
6. Подтверждённая оплата **идемпотентно** создаёт или обновляет ровно одну
   `FinanceTransaction` (связь через `finance_transaction_id`), поэтому
   повторное подтверждение не удваивает выручку. Обнуление или отмена платежа
   удаляет связанную транзакцию.

Интерфейс показывает, сколько суммы **ещё не распределено** по графику, и
блокирует добавление платежа, когда распределено всё.

### Комиссии

При полной оплате рассчитываются комиссии сеттера и клоузера по `PayrollRule`
и создаётся проект в разработке. Доход при этом **не создаётся повторно** — он
уже учтён транзакциями графика оплат.

## 7. Встречи и статусы

`Meeting` — встреча отдела продаж: назначает сеттер, проводит клоузер.
Поля: дата и время (UTC), адрес, клиент и телефон, **комментарий**, статус,
связь с лидом, родительская встреча (для перенесённых).

Поле «Комментарий» хранится в существующей колонке `notes` — второе поле того
же смысла не создавалось. В интерфейсе оно везде называется «Комментарий»,
доступно при создании, просмотре и редактировании, отображается в деталях
встречи. При переходе лида на этап «Встреча» комментарий тоже можно ввести.

### Статусы

| Значение | Подпись | Смысл |
|---|---|---|
| `scheduled` | Запланирована | Назначена, ещё не прошла |
| `closed` | Закрыт | Проведена, результат положительный |
| `minus` | Минус | **Проведена**, клиент отказался |
| `push` | Дожим | Проведена, требуется дожим |
| `rescheduled` | Перенёс | Перенесена на другую дату |
| `not_held` | **Не проведено** | Встреча **не состоялась** |

`Не проведено` ≠ `Минус` (встреча была, но проиграна) и ≠ `Перенесено`
(встреча перенесена). Статус присутствует в SQLAlchemy enum, PostgreSQL enum,
Pydantic-схемах, frontend-типах, действиях смены статуса, фильтрах, календаре,
таблице встреч, сводке клоузеров и аналитике.

Права: создание и редактирование — сеттеры и админы; смена статуса — клоузер
своей встречи или админ; удаление — автор-сеттер или админ.

## 8. Личные задачи и календарь

### Тип задачи

На личных досках задача имеет **структурированный тип** `kind`:

| `kind` | Подпись | Дополнительные поля |
|---|---|---|
| `task` | Обычная задача | — |
| `meeting` | Встреча | начало (обязательно), окончание, адрес/ссылка, комментарий |

`kind` **не переиспользует** свободное поле `task_type`, которое на доске
бэкенда хранит значения вида «API» и «Деплой» — это разные вещи.

Личная встреча появляется в личном календаре и **не создаёт CRM-встречу**:
личная встреча и встреча отдела продаж — разные доменные сущности.

### Drag-and-drop и ручная сортировка

- Перетаскивание за **отдельный drag handle** — случайный клик во время
  перетаскивания не открывает карточку; для чужих задач вместо ручки виден
  замок.
- Работают перенос между колонками и изменение порядка внутри колонки.
- Порядок сохраняется после обновления страницы.
- Сортировка ручная, в стиле Notion: позиция задаётся перетаскиванием.
- Оптимистичное состояние сразу отражает и `column_id`, и новый порядок;
  при ошибке API порядок откатывается и показывается toast.
- Backend **атомарно перенумеровывает** позиции затронутых колонок в
  последовательность `0…n−1` — без дублей и разрывов, что попутно лечит старые
  записи с одинаковыми позициями. Ответ возвращает все затронутые задачи.
- Перемещать можно только свои задачи (кроме админов и общих досок).

### Календарь

На странице «Мои задачи» два представления: **«Доска»** и **«Календарь»**.

Календарь показывает три визуально различимых внутренних источника:

| Источник | Что это |
|---|---|
| Задача | Личная задача со сроком (событие на весь день) |
| Личная встреча | Задача `kind=meeting` |
| Встреча CRM | Встреча, где пользователь сеттер или клоузер |

Клик по событию открывает соответствующую карточку: задача и личная встреча —
`TaskModal`, встреча CRM — `MeetingDetailModal`. Пользователя не перебрасывает
на общую страницу без выбранного события.

По умолчанию пользователь видит только свой календарь; администратор может
открыть календарь сотрудника на его странице.

Месячный календарь не обрезается: у `/api/meetings` лимит по умолчанию поднят
до 500 (максимум 1000) и добавлен заголовок `X-Total-Count`, а `/api/calendar`
отдаёт весь запрошенный диапазон целиком.

## 9. Календарь Nevocean

> **Nevocean использует собственный внутренний календарь с представлениями
> «День», «Неделя», «Месяц» и «Расписание». Google Calendar API и подключение
> внешнего аккаунта не используются.**

Расписание хранится и отображается самой системой. Внешних календарных
провайдеров, OAuth-подключений и хранения сторонних токенов нет.

### Режимы просмотра

| Режим | Что показывает |
|---|---|
| **День** | Вертикальная часовая сетка одного дня |
| **Неделя** | Семь дней, начиная с понедельника |
| **Месяц** | Сетка месяца с компактными строками событий |
| **Расписание** | Хронологический список, сгруппированный по дням |

Выбранный режим сохраняется в URL — `?calendarView=day|week|month|agenda`, —
поэтому открытие события и возврат назад не сбрасывают представление.

### Навигация

Кнопка «Сегодня», стрелки «предыдущий / следующий период», подпись текущего
диапазона и компактный date picker для перехода к конкретной дате. Шаг стрелок
зависит от режима: день — ±1 день, неделя — ±1 неделя, месяц — ±1 месяц.
Неделя начинается с понедельника, часовой пояс — `Asia/Bishkek`.

### Часовая сетка («День» и «Неделя»)

- Часы от `00:00` до `24:00`, шаг сетки — 30 минут.
- Начальная прокрутка примерно к `08:00`.
- Фиксированная колонка времени, заголовки дней, отдельная строка «Весь день».
- Текущий день выделен, поверх сетки — линия текущего времени.
- Вертикальная прокрутка; в недельном режиме на узких экранах — горизонтальная.

Событие располагается по времени начала и окончания. Обрабатываются:

| Случай | Поведение |
|---|---|
| Несколько событий в одно время | Делят ширину колонки поровну |
| Частичное пересечение | Отображаются рядом, а не друг поверх друга |
| Короткое событие | Минимальная высота и минимальный интервал столкновения, чтобы блок оставался читаемым и кликабельным |
| Событие без окончания | Продолжительность 60 минут по умолчанию |
| Переход через полночь | Обрезается по дню и показывается на обоих днях со стрелками `↑` / `↓` |

Раскладка пересечений выполняется в чистой функции `layoutDayEvents`
(`components/calendar/layout.ts`): события группируются в кластеры транзитивно
пересекающихся, внутри кластера жадно распределяются по колонкам, освободившаяся
колонка переиспользуется. Функция покрыта unit-тестами.

### Продолжительность встречи

У `Meeting` появилось поле `duration_minutes` (по умолчанию 60). Продолжительность
выбирается при создании и редактировании встречи; существующие встречи получают
безопасный fallback в 60 минут.

### Месяц

Внутри дня — компактные строки событий (время, цвет типа, сокращённое название),
первые три и ссылка `+N`, открывающая список всех событий дня. Обычные задачи со
сроком отображаются как события на весь день.

### Расписание

Хронологический список по дням: время, название, тип, статус, адрес или ссылка,
участник/клоузер. Дни без событий пропускаются. Реализованы состояния загрузки,
пустого списка и ошибки с кнопкой повтора.

### Создание событий по клику

| Экран | Клик по свободному слоту |
|---|---|
| «Мои задачи» | Создание **личной встречи** (`Task.kind = meeting`) с подставленными датой и временем. CRM-встреча при этом не создаётся |
| Календарь отдела продаж | Создание **CRM-встречи** с подставленными датой и временем; сохраняются клоузер, клиент, адрес, комментарий и продолжительность |

### Цвета и фильтры

Типы событий различаются цветом, CRM-встречи дополнительно окрашиваются по
статусу (запланирована, закрыта, минус, дожим, перенесена, не проведено).
Переключатели видимости типов только скрывают события в текущем календаре —
данные не удаляются.

В календаре отдела продаж есть фильтры по клоузеру, сеттеру, статусу встречи и
периоду (период задаётся текущим режимом просмотра), а также счётчики статусов
за период — это и есть отчётный срез по клоузерам.

### Переиспользуемое ядро

Два календаря не дублируют логику. Общее ядро — `components/calendar/`:

| Компонент | Роль |
|---|---|
| `Calendar` | Оркестратор: режимы, состояния, фильтрация по типам |
| `CalendarToolbar` | Навигация, date picker, переключатель режимов |
| `DayTimeGrid` / `WeekTimeGrid` | Часовая сетка (общий `TimeGrid`) |
| `MonthGrid` | Сетка месяца с `+N` |
| `AgendaView` | Список «Расписание» |
| `CalendarEventCard` / `CalendarEventChip` | Отображение события |
| `layout.ts` | Даты Asia/Bishkek, диапазоны режимов, раскладка пересечений |
| `useCalendarState` | Режим, якорная дата, видимость типов, синхронизация с URL |

Ядро используется во вкладке «Календарь» страницы «Мои задачи» и в календаре
встреч отдела продаж. Отличаются только источник данных, фильтры и действие
создания события.

### API

`GET /api/calendar` принимает точный диапазон `date_from` / `date_to`,
соответствующий выбранному представлению, — лишние месяцы не загружаются.
Слишком широкий (> 400 дней) или перевёрнутый диапазон отклоняется с 422.

Событие возвращается в унифицированном виде: `id`, `source`, `title`, `start`,
`end`, `all_day`, `status`, `location`, `description`, `editable`, `task_id`,
`meeting_id`, `lead_id`, `board_id`, а также ответственные (`owner`, `closer`,
`setter`) для отображения.

Права: сотрудник видит только свой календарь; admin/founder может открыть
календарь сотрудника; личные задачи других сотрудников через API не утекают;
календарь отдела продаж работает в рамках существующих прав отдела.

### Мобильная версия

На узких экранах по умолчанию открывается режим «День»; недельная сетка
прокручивается горизонтально; панель управления переносится по строкам и не
выходит за экран; переключатель режимов сжимается до иконок; часовая колонка
сохраняет читаемую ширину; события остаются кликабельными.

## 10. Профили и аватары

Профиль: имя, должность, цвет аватара, смена пароля, аватар и персональные
API-ключи для MCP-интеграции.

### Аватары

- Форматы: **JPEG, PNG, WebP**; ограничение размера — **5 МБ**.
- Сервер проверяет **реальное содержимое файла** (magic bytes), а не только
  заявленный MIME-тип.
- Имя файла генерируется сервером; пользовательское имя не используется.
- Изображение нормализуется: центральная квадратная обрезка, размер 512×512,
  перекодирование в WebP (попутно удаляются метаданные).
- Доступны замена и удаление; при отсутствии фото — fallback на инициалы и
  цвет.
- `avatar_url` присутствует во всех схемах пользователя и frontend-типах;
  общий компонент `Avatar` показывает фотографию **во всех местах системы** и
  сам возвращается к инициалам, если изображение не загрузилось.
- **Base64 в БД не хранится.** Файлы лежат на постоянном media-volume,
  раздаются nginx (в разработке — backend). Volume, конфиг nginx и `.gitignore`
  настроены; загруженные файлы в Git не попадают.
- Свой аватар меняет любой пользователь; чужой — администратор.

## 11. Уведомления и баг-репорты

### Уведомления (колокольчик)

Просроченные задачи, назначенные задачи, просроченные задачи общих досок (для
админов), встречи сегодня и на неделю, просроченные действия по лидам, лиды без
следующего действия, **просроченные оплаты из графика оплат**, недавние оплаты
и «минусы», риск кассового разрыва.

Просрочки оплат берутся **из графика**, а не из старого поля
`expected_payment_date`, поэтому корректно работают для частичных оплат и
многотраншевых сделок.

Сотрудник видит свои баг-репорты, админ — все. Статусы: `Новый`, `В работе`,

количество всех багов со статусом `new` и потому выглядел вечно непрочитанным.
Загрузка счётчика из `Shell` убрана, состояние и badge удалены. Статусы и
фильтры страницы не изменились. Совместимый endpoint `/api/bugs/count/new`
оставлен для внешних клиентов, но UI его больше не запрашивает. Это **не**
колокольчик уведомлений — он работает как прежде.

## 12. Атрибуция лидов

`source_id` (канал) сохранён и дополнен уточняющими полями:

| Поле | Назначение |
|---|---|
| `source_detail` | Уточнение источника (блогер, чат, рассылка) |
| `content_ref` | **Ссылка или ID конкретного рилса / публикации** |
| `utm_source`, `utm_medium`, `utm_campaign`, `utm_content` | UTM-метки |
| `external_lead_id` | Идентификатор лида в рекламной системе |

Поля доступны при создании и редактировании лида, в карточке, в таблице, в
поиске (по рилсу, кампании и внешнему ID) и в экспорте.

Для Instagram поле рилса/контента показывается явно. **Автоматическое
определение рилса не обещается** — интеграции с Meta нет, значения вводятся
вручную или приходят с UTM-метками.

### Будущая автоматизация (следующий этап)

Модель уже подготовлена под webhook, но фиктивная интеграция не создаётся.
План:

1. **Webhook Meta Lead Ads** — endpoint приёма лидов с верификацией подписки.
2. Сохранение `campaign_id`, `adset_id`, `ad_id`, `form_id` и creative/content
   ID (потребуется отдельная таблица `lead_ad_attribution`).
3. **Идемпотентность по внешнему lead ID** — фундамент уже есть:
   `external_lead_id` проиндексирован, повторное создание отклоняется 409.
4. Сопоставление creative/content ID с конкретным рилсом — справочник
   креативов, синхронизируемый из Meta Marketing API.
5. Хранение **минимально необходимого** raw attribution payload для
   диагностики, с ограниченным сроком хранения.
6. Защита webhook: проверка подписи `X-Hub-Signature-256` (HMAC-SHA256 с
   app secret), verify token при подписке, rate limiting, отклонение
   неподписанных запросов.
